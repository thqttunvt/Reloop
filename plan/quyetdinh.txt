5. STATE MACHINE (thay §15 của spec)
=====================================================================

LISTING:  ACTIVE → MATCHED → COMPLETED
          ACTIVE → EXPIRED (7 ngày) | CANCELLED (Owner)
          MATCHED → ACTIVE (giao dịch hủy/thất bại, còn hạn) | EXPIRED (hết hạn)

QUOTE:    như giaiphap.txt B1 (có INVALIDATED).

TRANSACTION:
  AWAITING_PAYMENT ──(bên trả bấm Thanh toán, đủ số dư)──▶ HANDOVER_PENDING
  AWAITING_PAYMENT ──(quá 12h / hủy)──────────────────────▶ CANCELLED
  HANDOVER_PENDING ──(đề nghị điều chỉnh giá)─────────────▶ PRICE_ADJUSTMENT_PENDING
  PRICE_ADJUSTMENT_PENDING ──(Owner đồng ý / từ chối)──────▶ HANDOVER_PENDING
  HANDOVER_PENDING ──(một bên xác nhận hoàn thành)────────▶ AWAITING_COUNTERPARTY (48h)
  AWAITING_COUNTERPARTY ──(bên kia xác nhận / quá 48h)────▶ COMPLETED   → tự mở khóa tiền
  AWAITING_COUNTERPARTY ──(bên kia khiếu nại)─────────────▶ DISPUTED    → đóng băng tiền
  HANDOVER_PENDING ──(hủy trước khi gặp)──────────────────▶ CANCELLED   → trả tiền bên trả
  HANDOVER_PENDING / PRICE_ADJUSTMENT_PENDING ──(báo thất bại)▶ FAILED  → trả tiền bên trả
  DISPUTED ──(Admin quyết, ≤ 7 ngày)──────────────────────▶ COMPLETED | FAILED

LỆNH NẠP (TopUp):   CREATED → CREDITED (webhook khớp) | EXPIRED (quá 24h không có tiền)
LỆNH RÚT (Withdrawal): REQUESTED → PROCESSING (Admin đang chuyển) → PAID (webhook tiền ra)
                       → FAILED (trả lại Khả dụng)

SỔ CÁI (append-only, bút toán kép — mỗi lần chuyển ghi 1 dòng trừ + 1 dòng cộng):
  TOPUP        ngân hàng ReLoop      → ví.available
  HOLD         ví.available (bên trả) → ví.held (bên trả)
  RELEASE      ví.held (bên trả)      → ví.available (bên nhận)
  REFUND       ví.held (bên trả)      → ví.available (bên trả)
  SETTLE (có phí) ví.held (bên trả) → ví.available (bên nhận) + REVENUE.available (hoa hồng)
                  + ví.available (bên trả, phần dư)
  LISTING_FEE  ví.available (Owner)   → REVENUE.available
  LISTING_FEE_REFUND  REVENUE.available → ví.available (Owner)
  FREEZE/UNFREEZE  đánh dấu trên khoản held của giao dịch tranh chấp
  WITHDRAW     ví.available           → ví.withdrawing → ngân hàng ReLoop (khi PAID)

BẤT BIẾN KIỂM TRA HẰNG NGÀY (job đối soát + CloudWatch alarm nếu lệch):
  Tổng (available + held + withdrawing) của mọi ví
    = Số dư thực tế TK ngân hàng ReLoop dành cho ví.
  Không ví nào có số dư âm.

7. QUYẾT ĐỊNH KỸ THUẬT TECH LEAD TỰ CHỐT
=====================================================================
TL-01  Tìm chi nhánh theo vị trí: geohash độ chính xác 4 (ô ~39 × 19,5 km), lấy ô chứa
       Listing + 8 ô lân cận = 9 Query, rồi lọc chính xác bằng Haversine ≤ bán kính.
TL-02  Tiền là số nguyên VND. Sổ cái append-only, bút toán kép; số dư ví là bản tổng hợp
       cập nhật CÙNG TransactWriteItems với bút toán và có ConditionExpression
       "available >= số tiền" → không bao giờ âm, không trừ trùng khi bấm 2 lần.
TL-03  Webhook ngân hàng: endpoint công khai không dùng JWT, xác thực bằng chữ ký / API key
       của nhà cung cấp; idempotent theo mã giao dịch ngân hàng; lưu raw payload để đối soát.
TL-04  Mọi thao tác tiền (thanh toán, rút, Admin quyết tranh chấp) bắt buộc Idempotency-Key
       và ghi audit log (ai, lúc nào, IP).
TL-05  API Admin cho tiền tách quyền riêng (role admin_finance) để demo nguyên tắc
       least privilege.
TL-06  API bổ sung, quy ước API, thiết kế DynamoDB, lịch EventBridge: theo giaiphap.txt
       mục C, E2, E3; bổ sung nhóm API ví:
         GET  /wallet                       (số dư 3 phần)
         GET  /wallet/ledger?cursor=        (lịch sử bút toán)
         POST /wallet/topups                (tạo lệnh nạp + VietQR)
         POST /transactions/{id}/pay        (giữ tiền)
         POST /wallet/withdrawals           (tạo lệnh rút)
         POST /bank-accounts                (khai STK, chờ Admin xác minh)
         POST /webhooks/bank                (webhook nhà cung cấp, không JWT)
         GET  /admin/withdrawals?status=    · POST /admin/withdrawals/{id}/mark-processing
         GET  /admin/reconciliation         · POST /admin/bank-accounts/{id}/verify
